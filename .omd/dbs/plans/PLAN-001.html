Goal

문서 잠금된 REL-001을 한 번에 구현한다: pnpm data:refresh 한 줄로 수집→정규화→DuckDB 적재가 끝나고, 계정≥3·체인≥1000·관측 append-only를 만족한다.

전제: PRD-001 · US-001~003 · F-001~007 · ADR-002 · POL-001~003 · REL-001 status=active (2026-08-09 잠금).

Approach

  • 기존 shared/crawler(fetch · discover · harvest · normalize · retention)를 감싸 오케스트레이션한다. 파서를 새로 쓰지 않는다
  • 계정 레지스트리는 accounts.json (F-001 / US-001)
  • 스토어는 DuckDB 단일 파일 (ADR-002 / F-007). JSONL은 원본, DuckDB는 재생성 가능 파생물
  • 화면·F-008은 만들지 않는다. 진행/실패는 CLI 로그 (US-002)

Steps

  1. F-001 — accounts.json 스키마·CRUD CLI (등록·중복 거부·비활성·last_fetched)
  2. F-002~F-004 — 레지스트리 기준 순차 수집(한 계정씩), POL-001 지터·백오프, 마지막 글 보강, 진행/실패 로그·실패 코드 재시도
  3. F-005~F-006 — normalize + retention, metrics append-only (덮어쓰기 금지, POL-003)
  4. F-007 — normalized → DuckDB 테이블(계정·체인·글·관측·유지율), 전체 재생성 경로
  5. 오케스트레이션 — pnpm data:refresh 엔트리, exit criteria 검증 스크립트(계정≥3, 체인≥1000, observed_at 누적)

Risks

  • 소프트 차단 — POL-001 준수, 우회 금지
  • 과거 metrics 스냅샷 유실 — append만, 삭제 금지 (POL-004와도 정렬)
  • DuckDB 의존성/네이티브 바인딩 — Node 환경에서 로드 확인

Verification

  • pnpm data:refresh 한 번으로 스토어까지 완료
  • 스토어 질의: 계정 ≥ 3, 체인 ≥ 1000
  • 동일 글 두 시점 관측이 공존 (append)
  • omd.mjs check 기획 문서 통과 유지

Out of this plan
