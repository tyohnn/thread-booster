Problem

  • 수집기는 이미 동작하지만, 산출물이 data_export/ 아래 JSON 파일로 흩어져 있어 조회하려면 매번 스크립트를 써야 한다
  • 2026-08-08 재수집에서 기존 체인 구성의 80%가 틀렸음이 드러났다. 정규화가 재현 가능해야 이런 정정이 안전해진다
  • 같은 글이 7주 만에 2.5배 성장한 사례가 있다. 관측은 덮어쓰면 안 되고 시계열로 누적돼야 한다

Outcome

한 줄 정의: 긁어낸 스레드 데이터를 한 번의 명령으로 수집·정규화·적재해, 대시보드가 바로 질의할 수 있는 단일 로컬 스토어를 유지한다.

Goals

  • 수집부터 적재까지 명령 한 줄로 끝난다
  • 어느 계정을 언제 어디까지 받았는지를 스토어만 보고 알 수 있다
  • 같은 입력으로 두 번 돌리면 같은 결과가 나온다

Non-goals

  • 실시간 동기화. 수동 실행으로 충분하다
  • 클라우드 DB·서버 운영
  • Notion 으로의 대량 적재 (→ ADR-001)
  • 수집 콘솔·계정 UI (F-008, PAGE-41/42) — REL-002 (v1.0)

Included stories

US-001 · US-002 · US-003 (REL-001). 화면 없이 CLI·accounts.json·로그로 수용한다.

사용자

  • 핵심: 데이터 운영자 (= 본인). 수집을 돌리고 실패를 확인한다
  • 보조: 대시보드 자체. 이 스토어를 읽는 유일한 소비자다 (v1.0)
  • 로컬 단독 실행. 계정·권한 구분 없음

핵심 사용자 흐름

  1. accounts.json에 팔로우할 계정을 추가한다
  2. pnpm data:refresh를 돌린다 — 신규 글 발견 → 퍼머링크 수집 → 2번·마지막 글 수집
  3. 정규화가 돌면서 체인이 재구성되고 관측이 누적되며 DuckDB 스토어가 재생성된다
  4. (v1.0) 대시보드를 새로고침하면 새 데이터가 보인다

범위

포함

  • 계정 레지스트리 파일 (팔로우 대상 관리)
  • SSR JSON 파싱 수집 실행·재시도·CLI 진행 표시 (ADR-004, POL-001)
  • 체인 재구성을 포함한 정규화 (POL-003)
  • 관측 시계열 append 적재
  • 마지막 글 조회수 보강 수집
  • DuckDB 단일 파일 스토어 (ADR-002)

제외

  • 수집 콘솔·계정 관리 화면 (→ REL-002)
  • 우리 계정 API 연동 (→ 이후 릴리즈)
  • DuckDB WASM 브라우저 적재 (대시보드 설계 시)

제약 및 의존성

  • 한 번에 한 계정만 수집한다 (POL-001)
  • 조회수는 퍼머링크에서만 나온다. 목록 페이지에는 없다
  • Threads 응답 구조가 바뀌면 파서가 깨진다
  • 수집 원문은 git에 올리지 않는다 (POL-002)

위험 요소

  • 소프트 차단 재발 — 지터·백오프·자체종료를 유지하고 차단 우회는 하지 않는다
  • 기존 스냅샷 손실 — 과거 metrics 스냅샷은 성장 비교의 근거다. 삭제 금지
