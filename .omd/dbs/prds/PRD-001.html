Problem

  • 수집기는 이미 동작하지만, 산출물이 data_export/ 아래 JSON 파일로 흩어져 있어 조회하려면 매번 스크립트를 써야 한다
  • 2026-08-08 재수집에서 기존 체인 구성의 80%가 틀렸음이 드러났다. 정규화가 재현 가능해야 이런 정정이 안전해진다
  • 같은 글이 7주 만에 2.5배 성장한 사례가 있다. 관측은 덮어쓰면 안 되고 시계열로 누적돼야 한다

Outcome

한 줄 정의: 긁어낸 스레드 데이터를 한 번의 명령으로 수집·정규화·적재해, 대시보드가 바로 질의할 수 있는 단일 로컬 스토어를 유지한다.

Goals

  • 수집부터 적재까지 명령 한 줄로 끝난다
  • 어느 계정을 언제 어디까지 받았는지를 스토어만 보고 알 수 있다
  • 같은 입력으로 두 번 돌리면 같은 결과가 나온다

Non-goals

  • 실시간 동기화. 수동 실행으로 충분하다
  • 클라우드 DB·서버 운영
  • Notion 으로의 대량 적재 (→ ADR-001 에서 배제 결정)

사용자

  • 핵심: 데이터 운영자 (= 본인). 수집을 돌리고 실패를 확인한다
  • 보조: 대시보드 자체. 이 스토어를 읽는 유일한 소비자다
  • 로컬 단독 실행. 계정·권한 구분 없음

핵심 사용자 흐름

  1. 계정 레지스트리에 팔로우할 계정을 추가한다
  2. 수집 명령을 돌린다 — 신규 글 발견 → 퍼머링크 수집 → 2번·마지막 글 수집
  3. 정규화가 돌면서 체인이 재구성되고 관측이 누적된다
  4. 대시보드를 새로고침하면 새 데이터가 보인다

범위

포함

  • 계정 레지스트리 (팔로우 대상 관리)
  • SSR JSON 파싱 수집 실행·재시도·진행 표시
  • 체인 재구성을 포함한 정규화
  • 관측 시계열 append 적재
  • 마지막 글 조회수 보강 수집 (약 640요청)

제외

  • 신규 글 자동 발견의 완전 자동화 (로그인 세션 필요 구간)
  • 우리 계정 API 연동 (→ v2.0)

제약 및 의존성

  • 한 번에 한 계정만 수집한다. 2026-08-01 병렬 수집이 소프트 차단을 불렀다
  • 조회수는 퍼머링크에서만 나온다. 목록 페이지에는 없다
  • Threads 응답 구조가 바뀌면 파서가 깨진다

위험 요소

  • 소프트 차단 재발 — 지터·백오프·자체종료를 유지하고 차단 우회는 하지 않는다
  • 기존 스냅샷 손실 — 06-12 / 08-02 스냅샷은 성장 비교의 유일한 근거다. 삭제 금지
